# Order («Бездна»): гайд для разработчика

Этот файл для тех, кто правит код системы. Здесь описано, где что лежит, как проходит бросок от кнопки до урона и что нужно знать, чтобы ничего не сломать. Правила игры — в рулбуке, здесь только код.

Foundry: v14. Язык кода: обычный JavaScript (ES-модули), без сборки. Файлы `.js` Foundry грузит как есть.

---

## 1. С чего начать

1. Прочитайте этот файл целиком (минут 15).
2. Откройте `module/README.md` — там карта папок.
3. Откройте `Order.js` и пролистайте хуки `init` и `ready`. Это оглавление всей системы: оттуда видно, какой модуль что регистрирует.
4. В начале каждого файла в `module/` есть комментарий: что делает файл и с чем связан. Читайте его перед правкой.

---

## 2. Как система загружается

Foundry читает `system.json`. В нём пять ES-модулей:

| Файл | Зачем |
|---|---|
| `Order.js` | Главный вход. Импортирует почти всё из `module/`. |
| `module/ui/OrderClientSettings.js` | Окно клиентских настроек. |
| `module/ui/OrderPlayerRating.js` | Рейтинг игроков. |
| `module/ui/token-hud/OrderTokenHud.js` | Token HUD (панель над токеном). |
| `module/mechanics/OrderTokenStealth.js` | Скрытность токенов. |

Что делает `Order.js`:

- **`init`** — классы документов (`OrderActor`, `OrderItem`, `OrderCombat`), `CONFIG.Order`, регистрация листов, настройки мира, скин окон и чата, хотбар, массовый бросок (Ctrl+R), хелперы Handlebars.
- **`ready`** — загрузка `debuffs.json` в `game.OrderDebuffs`, запуск веб-сокета (`initOrderSocket`), регистрация GM-обработчиков всех механик (`register…Bus()`), миграции, проверка магической усталости у всех актёров.
- **глобальные хуки** — оформление карточек чата, скрытие служебных сообщений, перки мастерства при росте характеристик, первичная настройка новых предметов.

Стили подключаются там же, в `system.json` → `styles`. Новый дизайн (листы X, чат, окна) лежит в `styles/order-*-x.css`.

## 4. Как проходит атака (на примере ближнего боя)

Почти все механики устроены одинаково. Разберём одну, остальные читаются так же.

Файл: `module/combat/OrderMelee.js`.

```
Игрок жмёт «Атака» в листе
        │
        ▼
createMeleeAttackMessage()      бросок атаки, карточка в чат
        │                       флаг flags.Order.attack, state: "awaitingDefense"
        ▼
Владелец цели жмёт кнопку защиты (.order-defense)
        │
        ▼
onDefenseClick()                бросок защиты на клиенте игрока
        │
        ▼
emitToGM({ type: "RESOLVE_DEFENSE", … })
        │                       уходит GM через core/socket.js
        ▼
GM: handleGMRequest() → gmResolveDefense()
        │                       сравнение: resolveDefenseHit() из core/dice.js
        │                       обновление карточки, кнопки урона
        ▼
Кто-то жмёт «Применить урон» → APPLY_DAMAGE → GM снимает ХП с учётом брони и крита
```

Почему через GM: игрок не может менять чужие документы (токен врага, чужую карточку, эффекты цели). Всё, что меняет чужое, делает клиент GM.

Где начинаются другие механики:

| Что | Файл | Функция-вход |
|---|---|---|
| Ближний бой | `combat/OrderMelee.js` | `createMeleeAttackMessage`, `createMeleeAoEAttackMessage` |
| Дальний бой | `combat/OrderRange.js` | `startRangedAttack` |
| Заклинание | `spells/OrderSpell.js` | `startSpellCast` |
| Навык | `skills/OrderSkill.js` | `startSkillUse` |
| Расходник | `items/OrderConsumable.js` | `startConsumableUse` |

После броска заклинание или навык уходит в «доставку» (`mechanics/OrderDeliveryPipeline.js`): атака по цели, область, спасбросок, массовый спасбросок, объект или зона, призыв. У каждого способа свой файл в `spells/` и `skills/` (`…Combat`, `…AOE`, `…Save`, `…MassSave`, `…Object`, `…Summon`).

## 5. Запросы к GM (веб-сокет)

Файл: `module/core/socket.js`.

**Как это работает:**

1. Модуль регистрирует обработчик своей шины на стороне GM: `registerGMHandler("meleeBus", fn)`.
2. Клиент игрока отправляет запрос: `sendToGM("meleeBus", { type: "RESOLVE_DEFENSE", … })`.
3. Запрос идёт по каналу `system.Order` одному активному GM. GM отвечает «получил» (ack) и вызывает обработчики шины.
4. Если ответа нет 4 секунды, запрос уходит запасным путём — скрытым сообщением в чат. Двойного выполнения не будет: у каждого запроса есть `requestId`.

Шины: `meleeBus`, `rangedBus`, `spellBus`, `skillBus`, `consumableBus`.

**Важно.** Веб-сокет включает строка `"socket": true` в `system.json`. Сервер Foundry читает её только при старте. После обновления системы **перезапустите сервер Foundry** (не просто F5 в браузере). Без перезапуска всё работает, но через запасной чат-путь, и в консоли будет предупреждение `Order | socket | GM не подтвердил запрос…`.

### Как добавить новый тип запроса

Допустим, в ближнем бою нужен запрос «снять щит с цели».

```js
// 1. В OrderMelee.js, в handleGMRequest(), добавьте ветку:
if (type === "DROP_SHIELD") return await gmDropShield(payload);

// 2. Напишите обработчик. Он работает на клиенте GM, поэтому может менять что угодно:
async function gmDropShield({ targetActorId, itemId } = {}) {
  const actor = game.actors.get(targetActorId);
  const item = actor?.items.get(itemId);
  if (!item) return;
  await item.update({ "system.inHand": false });
}

// 3. На клиенте игрока вызовите через уже готовую обёртку:
await emitToGM({ type: "DROP_SHIELD", targetActorId, itemId });
```

`emitToGM` сама решает: если вы GM, обработчик вызывается сразу, иначе запрос уходит по сокету.

Новую шину заводить не нужно. Если всё-таки нужна: добавьте её имя в `ORDER_BUSES` в `socket.js`, вызовите `registerGMHandler` в своей функции `register…Bus()` и вызовите эту функцию в `ready` в `Order.js`.

**Правило:** в payload передавайте id (актёра, токена, сообщения, предмета), а не сами документы. Документы по сокету не передаются.

## 6. Броски d20 и криты

Файл: `module/core/dice.js`. Чистые 1 и 20 проверяйте **только** через него: функции учитывают преимущество и помеху (kh/kl), то есть смотрят на кубик, который остался.

| Функция | Что делает |
|---|---|
| `d20FormulaForMode(mode)` | `1d20`, `2d20kh1` или `2d20kl1` по режиму броска |
| `isNaturalTwenty(roll)` | на d20 выпала чистая 20 |
| `isNaturalOne(roll)` | на d20 выпала чистая 1 |
| `resolveDefenseHit({ attackTotal, defenseTotal })` | попала ли атака: атака > защиты; ничья — в пользу защиты |
| `critFailTagHtml()` | метка `[КРИТ. ПРОВАЛ]` для строки результата |
| `critFailDefenseHtml()` | абзац «Крит. провал защиты» для карточки |
| `critFailAoECell(entry)` | класс и подсказка для ячейки в таблице АоЕ / массового спасброска |

**Критический успех (20)** влияет на механику: в карточке появляются кнопки крит-урона (удвоенный урон).

**Критическая неудача (1)** — только отображение. Исход броска не меняется, считается обычная сумма. В карточке появляется тёмная метка «КРИТ. ПРОВАЛ», в таблицах АоЕ — значок «1!», скин чата ставит штамп «Крит. провал». Так решила команда: последствия провала ГМ описывает сам.

Если когда-нибудь решите, что чистая 1 на защите — автоматическое попадание, это одна строка в `resolveDefenseHit`: `if (defenseNat1) return true;`. Комментарий над функцией об этом напоминает.

Как показать метку провала в новом месте:

```js
import { isNaturalOne, critFailTagHtml } from "../core/dice.js";

const nat1 = isNaturalOne(roll);
const line = `<p><strong>Результат:</strong> ${roll.total}${nat1 ? critFailTagHtml() : ""}</p>`;
```

Скин чата (`ui/OrderUiSkin.js`) сам найдёт класс `.order-crit-fail-tag` и поставит штамп. Стили метки — в `styles/order-ui-x.css`.

## 7. Эффекты и дебаффы

### Правила v14 (иначе будут предупреждения в консоли)

- Изменения эффекта читайте только через `getEffectChanges(effect)` из `core/effects.js`.
- Тип изменения — строка: `type: CHANGE_TYPES.ADD`. Не читайте `change.mode` и не используйте `CONST.ACTIVE_EFFECT_MODES`.
- Удаление ключа: `{ "flags.Order.x": _del }`, а не старое `"flags.Order.-=x": null`.

### Как система применяет эффекты

- `myCustomEffect.<Характеристика>Mod` (тип `custom`) — модификатор характеристики. Например, `myCustomEffect.StrengthMod` со значением `-3`. Глобальные хуки в `sheets/OrderPlayerSheet.js` (create/update/delete ActiveEffect) раскладывают такие изменения в `system.<Характеристика>.modifiers`. Хуки работают всегда, даже если лист закрыт.
- `flags.Order.roll.attack` / `flags.Order.roll.defense` — внешний модификатор к броскам атаки и защиты. Суммирует `getExternalRollModifierFromEffects`.

### Дебаффы со стадиями

Справочник — `module/debuffs.json`. Одна запись выглядит так:

```json
"MagicFatigue": {
  "name": "Магическая усталость",
  "icon": "…",
  "states":  { "1": "текст стадии 1", "2": "…", "3": "…" },
  "changes": { "1": [ { "key": "myCustomEffect.StrengthMod", "mode": 0, "value": "-3" } ], "2": […], "3": […] }
}
```

`"mode": 0` в файле — старая запись, Foundry сам переводит её в `type: "custom"`.

Эффект дебаффа на актёре помечен флагами `flags.Order.debuffKey` (ключ из json), `stateKey` (текущая стадия) и `maxState`. По ним Token HUD (`ui/token-hud/tokenDebuffHud.js`) и механики находят дебафф и меняют стадию.

Чтобы добавить новый дебафф, достаточно новой записи в `debuffs.json`. Код трогать не нужно: HUD и выпадающие списки читают файл.

## 8. Магическая усталость (МУ)

Файл: `module/mechanics/OrderMagicFatigue.js`.

**Правило.** Предел МУ = 3 + Магия + Выносливость (рулбук, с. 130). Если МУ выше предела, на актёре висит дебафф «Магическая усталость»:

| Превышение | Стадия | Штраф |
|---|---|---|
| +1 | 1 — Магическая усталость | −3 |
| +2 | 2 — Магическая изнеможденность | −6 |
| +3 и больше | 3 — Магическая ломка | −12 |

**Как работает автоматика:**

- Стадия зависит только от разницы `ManaFatigue.value − ManaFatigue.max`. Неважно, откуда пришло изменение: каст, ввод в листе, HUD, эффект, снижение Магии.
- `OrderActor.prepareData()` вызывает `syncManaOverflowDebuff(this)`. Если стадия уже верная, функция выходит сразу и ничего не пишет.
- Каст больше не обрезает МУ по пределу: превышение хранится в самом значении. Перед кастом сверх предела игрок видит окно, где написано, какая стадия будет.
- Эффект бессрочный и помечен `flags.Order.manaOverflow`. Стадия ходит за превышением в обе стороны; при превышении 0 эффект снимается.
- Если ГМ повесил дебафф руками, автоматика его не снимает и не понижает. Она только поднимет стадию, если превышение больше, а потом вернёт ручную.

## 9. Запись в базу из prepareData — только через side-effects.js

`Actor.prepareData()` выполняется на **каждом** подключённом клиенте, причём часто, например при каждом движении токена. Если писать оттуда в базу без проверки, будет беда: эффект создастся по разу от каждого игрока, а у игроков без прав посыплются ошибки «lacks permission».

Поэтому перед любой записью из `prepareData()`:

```js
import { shouldPersistActorSideEffects } from "../core/side-effects.js";

if (!shouldPersistActorSideEffects(actor)) return; // пишет только один клиент
await actor.update({ … });
```

Пишет активный ГМ с наименьшим id. Если ГМа нет в игре — первый активный пользователь с правами на актёра.

Так уже сделаны перегруз инвентаря (`OrderActor._handleOverloadEffects`) и магическая усталость.

## 11. Миграции

Папка `module/migrations/`. Запускаются в `ready`, только у ГМа. Каждая хранит номер версии в настройке мира и не запускается повторно.

| Файл | Что делает | Версия |
|---|---|---|
| `OrderSpellMigration.js` | дописывает заклинаниям поля доставки | `MIGRATION_VERSION` |
| `OrderSkillMigration.js` | то же для навыков | `MIGRATION_VERSION` |
| `OrderCleanupMigration.js` | убирает устаревшие поля, чинит старое оружие и броню | `static VERSION` |

Чтобы миграция прошла ещё раз (например, вы поменяли правила), увеличьте номер версии в файле.

## 12. Отладка

- **Консоль браузера** (F12). Сообщения системы начинаются с `Order |`.
- **Сокет.** Предупреждение `Order | socket | GM не подтвердил запрос…` значит, что сервер не перезапущен после обновления `system.json` или ГМа нет в игре.
- **Ближний бой.** В `combat/OrderMelee.js` стоит `ORDER_DEBUG = true`: каждая атака пишет в консоль строки `OrderMelee[DBG]`. Выключите, когда не нужно.
- **Данные актёра.** В консоли: `game.actors.getName("Имя").system`.
- **Эффекты актёра.** `game.actors.getName("Имя").effects.map(e => [e.name, e.flags.Order])`.
- **Дебаффы.** `game.OrderDebuffs` — загруженный `debuffs.json`.
- **Изменения не видны после правки файла.** Foundry кэширует модули. Нужна жёсткая перезагрузка (Ctrl+F5), иногда — перезапуск сервера.

## 13. Чек-лист ручной проверки

После заметных изменений пройдите в мире с двумя клиентами: ГМ и игрок (второе окно браузера, другой пользователь).

1. Игрок атакует врага в ближнем бою. Защищается уворотом, блоком, заклинанием. Урон проходит.
2. Дальняя атака, в том числе по области.
3. Заклинание: атакой, по области, со спасброском, массовым спасброском, зоной, призывом.
4. Навык: те же варианты.
5. Расходник (зелье) на себя и на цель.
6. Выбросите 1 на d20 (в консоли: `CONFIG.Dice.randomUniform = () => 0.999` — все кубики будут падать единицей; вернуть — F5). В карточке есть «КРИТ. ПРОВАЛ», исход не изменился.
7. Каст сверх предела МУ: в окне подтверждения написана стадия, после каста на актёре дебафф нужной стадии. Сбросьте МУ в листе — дебафф снимается.
8. Повесьте дебафф через Token HUD, поменяйте стадию, снимите.
9. В консоли нет красных ошибок и нет `Order | socket | GM не подтвердил…`.

## 14. Частые ошибки

- **Переносы строк.** В репозитории включён `core.autocrlf=true`, файлы на диске с CRLF. Если скрипт пишет `\r\r\n`, git начинает считать файл бинарным. Пишите либо LF, либо ровно CRLF.
- **Свой d20-код.** Не проверяйте `roll.dice[0].results[0].result === 20` руками: при преимуществе это может быть выброшенный кубик. Есть `isNaturalTwenty` / `isNaturalOne`.
- **Хук чата.** Используйте `renderChatMessageHTML` (получает `HTMLElement`). `renderChatMessage` устарел.
- **Запись в чужие документы с клиента игрока.** Не сработает. Отправляйте запрос ГМу (раздел 5).
- **Запись из prepareData без проверки.** См. раздел 9.
- **`packs/`.** Это база LevelDB. Не правьте и не коммитьте вручную, пока Foundry запущен.
